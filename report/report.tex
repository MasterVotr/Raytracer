\section{Problem Definition and Sequential Solution}

\subsection{Problem Definition}
This work focuses on the optimization and parallelization of the algorithm for constructing the BVH (Bounding Volume Hierarchy) acceleration data structure. This structure is crucial for the efficient execution of raytracing. The Raytracer was developed within the NI-PG1 course. The goal is to minimize the tree construction time (Build time) on multi-core x86 architecture processors using OpenMP and vectorization.

\subsection{Sequential Algorithm and Implementation}
The starting point is the sequential implementation of BVH. The project implements the \texttt{BvhNaive} variant and the more optimized \texttt{BvhSeq} / \texttt{BvhSeq2} variants (\texttt{BvhSeq} was found too complicated and slower and was rewritten into \texttt{BvhSeq2}).

The construction algorithm works using the \textit{Top-Down} method:
\begin{enumerate}
    \item Start with the root node containing all scene triangles.
    \item For each node, find the best split plane.
    \item The SAH (Surface Area Heuristic) is used to determine the split cost:
    \begin{equation}
        Cost = C_t + \frac{S_L}{S_{parent}} \cdot N_L \cdot C_i + \frac{S_R}{S_{parent}} \cdot N_R \cdot C_i
    \end{equation}
    \item If the split cost is lower than the leaf cost and the maximum BVH tree parameters are not reached, the triangles are split, and the construction is recursively called for the left and right children.
\end{enumerate}
Where $C_t$ is traversal cost, $C_i$ is the cost of an intersection with a node and $S$ is the surface area of the node bounding box (combination of all triangle boudning boxes in one node).

The \texttt{BvhSeq2} implementation uses the \textit{Binning} technique, which reduces the number of tested split planes, thereby speeding up SAH evaluation compared to the naive approach where all triangle edges are tested [1].

The number of bins used is 16, Maximum depth of the BVH tree is 32 and the maximum numnber of triangles in a leaf is 4.

\paragraph{BvhNode} structure was designed to be memory efficient (32 bytes) and aligned for better cache utilization. It is used by all the implementation versions. \texttt{Vec3} is a custom structure of 3 single precision floating point numbers used for calculations. In practice \texttt{\detokenize{size_t}} is used instead of \texttt{int}, that could be improved to truly fit inside 32 bytes of memory.

\begin{lstlisting}
struct BvhNode {
    Vec3 aabb_min;
    Vec3 aabb_max;
    int t_begin;  // or left child (right child is t_begin+1)
    int t_count;
};
\end{lstlisting}

\paragraph{AABB} is a datastructure that holds the minimum and maximum 3D points of a bounding box. It also has a few helpful methods like \texttt{surface\_area()} and \texttt{expand()} used in binning and other calculations.

\begin{lstlisting}
struct AABB {
    Vec3 min;
    Vec3 max;
    float surface_area();
    void expand(AABB other);
    void expand(Vec point);
};

\end{lstlisting}

\section{Parallelization and Optimization (Vectorization and OpenMP)}

This chapter describes the algorithm modifications for parallel processing on the CPU (implementations \texttt{BvhPar}, \texttt{BvhPar2}).

\subsection{Compiler flags}

As per usual the compiler is a lot smarter than I am when it comes to optimization, so the lowest hanging fruits were optimized by it. When creating \texttt{BvhVec} I used the compiler with flags \texttt{-ftree-vectorize -fopt-info-vec -fopt-info-vec-missed} to get hints of were to adjust my code and where to use SoA.

When I was developing \texttt{BvhVec2} the usage of these flags was minimal due to my choice to use vector in a different approach. This meant that the compiler might not have been able to optimize my code further in some parts.

For the whole code base I used these compiler flags: \texttt{-O3 -ffast-math -funroll-loops}. Enabeling the agressive optimization decresed the build time significantly, without hindering the build quality (the result was the same BVH tree).

For SIMD instructions and other intrinsic families I used the \texttt{-march=native} compiler flag, so it could choose the vectorization family, that would fit the architecture the code was compiled on the best.

\subsection{Additional Data Structures:}
In this section I will describe the data structures used in the vectorized and parallel version.

\paragraph{vAABB} is an alternative AABB structure, that is used for holding the minimum and maximum 3D points in SIMD 128-bit vectors.
\begin{lstlisting}
struct vAABB {
    __m128 aabb_min;
    __m128 aabb_max;
};
\end{lstlisting}

\paragraph{Job} is a helpfull datastructure to hold data needed for starting up a parallel task on a separate thread.
\begin{lstlisting}
struct Job {
    size_t node_idx;
    int depth;
    AABB cb;
};
\end{lstlisting}

\subsection{Vectorization}

As part of the optimization, the possibility of vectorization (AVX/SSE SIMD instructions) was explored in the \texttt{BvhVec} and \texttt{BvhVec2} implementations.

\paragraph{BvhVec} was the first variant implemneted. It uses SIMD instructions from the AVX familily with 256-bit registers (holding f32x8). When implementing I first wanted to lean of the compiler to do the vectorization for me, but for any more sophisticated loops it was unable to identify the safety and I was forced to vectorize thses loop manully.

The structure of arrays (SoA) pattern was used to increase cache locality - reduce the amount of cache misses and increase the amount of continuous memory reading. This was to a great effect when it came to paralelizing the binning phase of the algorithm. However when it came to the initial triangle bounding box and centroid calculation the restructuralization of the data greatly overshadowed the cost reduction from vectorization, so much so, that it almost negated the performance gain in the binning phase.

The vectors always contain subsequent values of data. For example holding 8 position Xes of the min position of a bounding box. Resulting in 8 bounding boxes being loaded, calculated and stored at once.

\paragraph{BvhVec2} uses a different approach. The crucial difference is in the usage of 128-bit vector registers from the SIMD familily (holding f32x4). Instead of holding subsesquent values of data, the each vector holds one 3D point (x, y, z, 0), with the last element not being used. This changed the SoA to a diffent, more readable and easier to work with format. On the other hand it forced me to do all the vectorization manually, since this is not the "natural" way of vector usage.

The initial calculation of triangle bounds and centroids is now much faster, however the binning and findnig a best split calculations are basically on par with the sequential version. The centroid bounds recalculation si slower then the sequential version, so I have erased it from the implementation.

\section{Conclusion}

Within the semester project, the BVH tree construction was implemented and optimized.
\begin{itemize}
    \item \textbf{Sequential Version:} Implementation with Binning (\texttt{BvhSeq2}) is approx. 2x faster than the naive version.
    \item \textbf{Parallel Version:} The \texttt{BvhPar2} version using OpenMP Tasks reached a speedup of up to \textbf{XX-times} compared to the sequential version when using YY threads on the test machine.
\end{itemize}

The most performant implementation proved to be \texttt{BvhPar2} (or \texttt{BvhPar2v}), which combines an efficient algorithm (Binning) with task-level parallelization.
